# ADR-0008 — 문서 계층

- 소유 문서: [문서 계층 설계](../../docs/internals/doc-hierarchy.md)
- 근거: 사용자 요청 "폴더 구조 같은데 계층도 추가할 수 있도록 설계", [레퍼런스 조사](../../devlog/_plan/261107_docs_plus_shortcuts_tree/evidence/refs.md), [계획 감사](../../devlog/_plan/261107_docs_plus_shortcuts_tree/001_audits.md).

## 결정 기록

- 목적: 독립 문서를 폴더처럼 묶고 옮겨요.
- 선택: 노션식 "문서가 곧 부모". `docs.parent_id`·`position`·`archived_with` 칸. 독립 문서만, 8단, 순환·깊이 불변식은 보관 문서까지 저장된 그래프 전체에, 형제 순서는 정수(쓰기 때 그 묶음을 다시 매김), 부모 보관 때 자손도 함께(되살리면 함께).
- 거울: 부모 파일 이름의 폴더(옵시디언 폴더 노트 관례), 쓴 폴더 조각을 ledger 에 저장, 4단·절대 1000바이트 한계. 맨 위 문서의 경로·내용은 바뀌지 않아요. 하위 트리 이동은 ref 마다 따로(부분 성공).
- 계약: 더하기만. `/api/act` 의 `doc` 은 parent 를 생략하면 지금과 같아요. 만들기 멱등 해시는 parent 를 보낸 요청에만 parent 를 넣어요. `parent` 속성 이름은 새로 못 만들고, 있던 것은 검색·정렬·지우기가 그대로예요.
- 검토한 대안: 폴더 엔티티(빈 그릇이 하나 더 생김), 태그 경로(여러 곳·순서·이동 없음), ref 키 배치 표(일·사건까지 넣을 때나 필요), 분수 인덱스 순서 키(형제 묶음이 작아 다시 매기기가 더 단순).
- 남는 위험: 깊은 트리의 하위 트리 다시 쓰기가 거울 큐를 길게 만들어요(한 owner 직렬 큐). 바깥에서 고친 거울 파일이 있으면 그 문서의 거울만 사람이 해소할 때까지 옛 경로에 남아요.

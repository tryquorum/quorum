# 모바일 정보 구조(IA)

iOS 앱이 웹의 모든 경험을 어떤 화면 구조로 담는지, 왜 그렇게 정했는지 적어요. 웹과 기능별 대조, 레인별 담당, 파일 경계는 [iOS 동등 로드맵](../../devlog/_plan/261107_ios_parity/000_roadmap.md)에, 결정 기록은 [ADR-0010](../../structure/decisions/ADR-0010-mobile-ia.md)에 있어요. 라우트 이름과 인자의 원본은 [routes.ts](../../apps/mobile/src/navigation/routes.ts), 딥링크 해석은 [linking.ts](../../apps/mobile/src/navigation/linking.ts)예요.

## 탭

매일 들어가는 곳만 탭에 둬요. 웹이 운영 순회를 주 메뉴에서 설정으로 옮긴 것과 같은 기준이에요.

- 최종 탭: **홈 · 전체 · 문서 · AI · 검색**. 검색은 웹 ⌘K 의 자리라 화면·명령·설정·일·사건·문서를 한 입구에서 찾아요.
- 설정은 탭에서 빠지고 홈 머리의 톱니, 검색 결과로 가요. 루트 쌓기의 `Settings` 화면이에요.
- 바꾸는 때: 검색이 실제로 동작할 때 레인 3 이 [tabs.ts](../../apps/mobile/src/navigation/tabs.ts)에서 설정 탭을 검색 탭으로 바꿔요. 그 전까지는 지금처럼 설정 탭이 있어요. 비어 있는 탭을 내보내지 않으려는 순서예요.
- 판 전환(개인·회사)은 홈·전체 큰 제목 옆 메뉴예요. 보드 캔버스(메모·글·영역·연결과 배치)는 전체 머리에서 여는 `Board` 화면이에요. 폰 폭에서는 확대·축소로 훑고, 항목은 눌러서 시트로 고치고, 길게 눌러 끌어 옮겨요.

## 쌓기와 상세

- 탭마다 네이티브 쌓기(native-stack)가 있어요. 루트는 그 탭 화면이에요.
- 공용 상세(일 `Work`, 문서 `Doc`, 목표 목록, 결정 칸, 문서 폴더, AI 대화, 설정 섹션, 지난 순회)는 모든 탭 쌓기에 같이 등록해요. 홈에서 연 일은 홈 쌓기에 쌓이고 뒤로가 홈에서 끝나요. 다른 탭으로 갔다 와도 쌓인 자리가 남아요.
- 설정은 탭이 아니라 루트 쌓기의 `Settings` 안 쌓기예요. 그 안에도 공용 상세를 같이 등록해서 설정 섹션·지난 순회·순회 대화가 설정 위에 쌓이고, 설정 루트의 뒤로가 탭으로 돌아가요(검색 결과의 설정 항목은 `Settings › SettingsSection` 으로 열어요).
- 지금 탭을 다시 누르면 루트로 돌아가요.
- 상세의 머리는 보통 제목과 뒤로(왼쪽 가장자리 스와이프 포함)예요. 탭 루트는 큰 제목이에요. 머리 아래 그림자 선은 그리지 않아요.
- 하단 필은 탭 루트에서만 보여요. 쌓인 화면에서는 숨겨서 본문과 아래 동작 줄에 자리를 줘요. 숨김은 `TabPill` 이 지금 탭의 쌓기 깊이를 읽어 한 곳에서 정해요(화면마다 탭 막대 옵션을 바꾸지 않아요). 탭 쌓기의 중첩 state 는 처음 그려지기 전이나 딥링크 직후 잠깐 비어 있을 수 있어서, 비어 있으면 루트로 봐요.

## 엄지 영역과 입구

- 자주 누르는 동작은 화면 아래쪽에 둬요: 탭 필, 필 옆 + 원 단추(빠른 추가), 상세의 아래 동작 줄(끝냄·보내기 등).
- 머리 오른쪽에는 드물게 쓰는 동작만 둬요(톱니, 필터, 보기 바꾸기).
- 목록 화면의 찾기는 머리의 네이티브 검색창(끌어내리면 보임)이에요.
- 빠른 추가는 웹과 같은 두 입구예요: 홈·전체 맨 위 한 줄, 그리고 어디서나 여는 상세 시트(루트 쌓기의 `QuickAdd` 시트 라우트). 탭 루트에서는 필 옆 + 원 단추로, 필이 숨은 쌓인 화면에서는 머리 오른쪽 ⋯ 메뉴(`HeaderMenu`)의 "빠른 추가"로 열어요.

## 시트·스와이프·길게 누르기

- 시트: 짧은 입력과 고르기는 아래에서 올라오는 시트예요(iOS pageSheet). RN Modal 은 `allowSwipeDismissal` 과 `onRequestClose` 가 함께 있어야 끌어내려 닫혀서 `Sheet` 부품이 둘 다 줘요. 여러 화면에서 여는 전역 시트(빠른 추가)는 루트 쌓기 라우트, 한 화면 안의 고르기·편집은 `Sheet` 부품이에요.
- 스와이프: 되돌릴 수 있는 한 동작만 둬요(끝냄/다시 열기, 처리, 미루기). 지우기·보관처럼 거두기 어려운 동작은 스와이프에 두지 않고 길게 누르기 + 확인으로 해요. 스와이프한 결과에는 되돌리기 토스트를 띄워요.
- 스와이프와 다른 제스처의 순서: 가로 이동이 12pt 를 넘고 세로의 2배보다 클 때만 행이 잡아요. 그 전에는 세로 스크롤이 먼저예요. 화면 왼쪽 가장자리 24pt 에서 시작한 끌기는 쌓기의 뒤로 제스처에 맡겨요. 행이 잡은 뒤에도 스크롤이 가져가겠다고 하면 놓아요. 길게 누르기는 움직이지 않았을 때만 열려요. 새 네이티브 제스처 모듈 없이 RN PanResponder 로 만들어서, 이 순서는 시뮬레이터에서 직접 확인해요.
- 길게 누르기: 그 행의 모든 동작 목록(iOS 동작 시트)이에요. 스와이프에 있는 동작은 길게 누르기와 상세에도 있어요. VoiceOver 사용자는 같은 동작을 접근성 동작으로 고를 수 있어요.
- 당겨서 새로고침: 서버 데이터를 보여 주는 모든 스크롤 화면.

## 데이터

- 같은 REST 계약(`packages/contracts`)과 서버 권한 규칙을 써요. 모바일만을 위한 서버 경로는 만들지 않아요(로그인 `/api/mobile/auth` 는 예외, [ADR-0006](../../structure/decisions/ADR-0006-ios.md)).
- 읽기는 공용 캐시([query.ts](../../apps/mobile/src/api/query.ts))를 거쳐요. 캐시는 "서버 주소 + 로그인 주체(Access 토큰의 이메일, 없으면 익명)" 로 나눠요. 로그인·로그아웃·만료로 주체가 바뀌면 그 전 캐시를 버리고, 그 전에 떠난 읽기의 결과도 받지 않아요. 같은 서버에서 계정을 바꿨을 때 앞 계정의 데이터가 "마지막 값" 으로 남지 않게 하려는 거예요.
- 홈과 전체처럼 같은 데이터를 읽는 화면이 한 번의 요청을 나눠 쓰고, 한 화면에서 바꾼 값이 다른 화면에도 바로 보여요. 다시 읽기가 실패해도 마지막 값을 지키고 위에 한 줄로 알려요(웹 data-state 와 같음). 화면에 들어올 때, 앱이 앞으로 돌아올 때, 당겨서 새로고침할 때 다시 읽어요. 웹처럼 몇 초마다 폴링하지 않는 것은 배터리와 셀룰러 때문이에요. 진행 중인 AI 실행을 지켜보는 화면만 보이는 동안 짧게 폴링해요.
- 읽기와 쓰기가 겹치면 쓰기가 이겨요. 진행 중인 낙관적 쓰기는 캐시에 "덧씌울 변경"으로 남아 어떤 읽기 결과(첫 읽기 포함)가 와도 그 위에 다시 얹혀요. 읽기를 보낸 뒤 끝난 쓰기가 있으면 그 읽기 결과는 버리고 다시 읽어요. 데이터가 아직 없을 때의 첫 읽기만은 덧씌운 채 받아 두고 곧바로 다시 읽어요. 웹 `useBoard` 의 쓰기 세대·저장 중 항목 보호와 같은 성질이에요.
- 판 항목 쓰기는 낙관적이에요. 캐시를 먼저 바꾸고, 같은 항목을 연달아 바꾸면 요청은 순서대로 하나씩 가고 마지막 쓰기가 화면을 정해요. 실패하면 그 값이 아직 화면에 있을 때만 서버가 확인한 값으로 되돌리고 토스트로 알려요. 실패한 쓰기는 자동으로 다시 보내지 않아요.
- 쓰기 실패는 세 가지로 나눠요. 409 는 `ConflictError` 이고 응답 본문 전체를 들고 있어요. 본문 모양은 경로마다 달라서(노트·문서는 `current`, 순회 지시문은 `ops`, 같은 AI 정리는 `run`, 그 밖은 오류 글만) 화면이 종류별로 읽고, 현재 값이 없으면 다시 읽어요. 서버가 확실히 거절한 4xx(서버 `err()` 의 JSON `{error}` 본문, Access 로그인 요구)만 "쓰이지 않음"이에요. 그 밖의 모든 실패(네트워크 오류, 5xx, 프록시가 만든 JSON 아닌 4xx, 읽지 못한 응답)는 `UnknownWriteError` 로, 쓰였는지 몰라요. 판 항목은 되돌린 뒤 다시 읽어 실제 값을 보여 줘요.
- 노트처럼 사람 글이 걸린 쓰기는 낙관적 되돌림을 쓰지 않아요. 초안을 늘 보존하고 409·결과 불명이면 자동 저장을 멈추는 노트 저장 상태 기계를 따로 써요(아래 "노트 편집"). 웹의 HTML 저장 상태 기계 `NoteSaver` 는 [note-save.ts](../../packages/contracts/src/note-save.ts)로 옮겨 웹과 iOS 가 같은 파일을 볼 수 있게 했어요(iOS 가 HTML 원본을 고칠 때 씀).
- 로그인(Access 토큰)·서버 주소는 [auth.tsx](../../apps/mobile/src/auth.tsx)와 [storage.ts](../../apps/mobile/src/storage.ts)가 맡아요.

## 노트 편집

노트는 웹 편집기(Tiptap)가 만든 HTML 이 원본이고, iOS 는 마크다운으로 고쳐요. 서버가 md 로 HTML 을 다시 만들기 때문에, 사람이 웹에서 넣은 서식을 iOS 저장이 덮지 않게 두 겹으로 지켜요. 공용 모듈은 `apps/mobile/src/notes/` 이고 레인 1(일 노트)·레인 2(문서 노트)가 같이 써요.

- 기존 노트는 서버가 판정해요. `GET /api/docs/:ref/note` 의 `markdownEditable`(REST 만, [계약](../../packages/contracts/src/docs.ts) 선택 필드)은 html 이 비었거나, 엄격 HTML→md 변환이 성공하고 그 결과가 저장된 md 와 정규형이 같고 다시 만들어도 같은 md 이며, 원래 html 과 md 로 다시 만든 html 의 서식 모델(블록·굵게·기울임·취소선·코드·링크·이미지·줄바꿈·할 일 체크)이 같을 때만 true 예요([ops.ts](../../apps/server/server/docs/ops.ts), [note-model.ts](../../apps/server/server/docs/note-model.ts)). 마지막 비교는 엄격 변환기가 오류 없이 조용히 버리는 서식(맞붙은 강조, 줄바꿈 걸친 강조, 글자 색)을 잡으려는 것이고, 모르는 태그·속성이 있으면 false 예요. 엄격 변환기가 꽂혀 있지 않거나 필드가 없는 옛 서버면 false 로 봐요.
- false 면 iOS 는 읽기만 하고 이유를 띠로 알려요(`noteEditability`). 클라이언트에서 HTML 을 다시 판정하지 않아요.
- 새로 쓰는 초안은 저장할 때마다 허용 문법([mdPolicy.ts](../../apps/mobile/src/notes/mdPolicy.ts))을 검사해요. 표, HTML 태그, 언어를 적은 코드 블록(서버가 `class` 를 만들어 웹 편집기가 읽기 전용이 됨), 각주, 참조 링크, 밑줄 제목, 허용 밖 링크 주소는 보내지 않고 그 줄과 이유를 보여요.
- 저장은 `POST /api/docs/:ref/write {mode:'replace', md, expectedVersion}` 하나예요. 상태 기계([noteSaver.ts](../../apps/mobile/src/notes/noteSaver.ts))는 웹 NoteSaver 와 같은 뜻이에요: 409 면 충돌(서버 current 보관), 응답 유실·버전 없음이면 불명으로 자동 저장을 멈추고 다시 보내지 않아요. 새로 불러온 서버 노트는 자동으로 깨끗한 상태가 되지 않고, 사람이 내 초안을 내보낸 뒤에만 채택해 직접 합쳐요(merging). 채택한 노트가 편집 불가면 읽기로 바뀌고 내 초안은 보관돼요. 같은 화면의 제목·속성 쓰기가 올린 version 은 깨끗하고 기준이 같을 때만 따라가요.
- 초안은 "서버 주소 + 확인한 계정 이메일 + ref" 별 파일로 보관해요([drafts.ts](../../apps/mobile/src/notes/drafts.ts)). 계정을 모르거나 쓰기에 실패하면 보관을 확인하지 못했다고 알려요. 저장 중에 꺼진 초안은 불명으로 복원돼요.
- 읽기 화면([NoteView.tsx](../../apps/mobile/src/notes/NoteView.tsx))은 같은 문법 범위를 RN 글로 그려요. 인용·코드는 옅은 바탕으로 나누고, 할 일 체크는 편집할 수 있는 노트에서만 눌려요. 이미지 주소에는 요청과 같은 규칙으로만 로그인을 붙여요(같은 https 서버일 때).

## 딥링크

앱 스킴은 `direction://` 예요(app.config.ts). 웹 주소와 같은 모양을 써요.

| 링크 | 열리는 곳 |
|---|---|
| `direction://w/<ref>` | 홈 쌓기의 일 상세(웹 `#/w/<ref>`) |
| `direction://docs/<ref>` | 문서 쌓기의 문서 페이지(웹 `#/docs/<ref>`) |
| `direction://home`, `list`, `docs`, `ai`, `settings` | 그 탭 루트 |

ref 는 한 경로 조각으로 인코딩해요(`item:<판>:<id>` 의 콜론 포함). 로그인 콜백 `direction://auth` 는 보통 로그인 창(ASWebAuthenticationSession)이 가로채지만, 로그인 창 밖에서 들어오는 경우를 위해 linking `filter` 로 내비게이션에서 빼요. 그 링크로는 화면이 바뀌지 않고 로그인도 되지 않아요(state 를 아는 로그인 창만 토큰을 받아요).

## 왼쪽 선과 위계

카드·행·절·노트·인용·기록에 장식으로 붙는 왼쪽 세로선(왼쪽 테두리, 표시선, 타임라인 줄)은 iOS 에서 쓰지 않아요. 위계는 여백, 글자 무게, 바탕(묶음 배경)으로 나타내요.

- 묶음(`Section`)은 테두리 없는 둥근 바탕이고, 안의 행은 들여쓴 가는 가로 구분선으로 나눠요.
- 강조(결정 대기, 경고)는 앞 표시(점·아이콘)와 글자 색으로 해요. 색만으로 알리지 않고 글을 함께 둬요([디자인 코어](design-core.md)).
- 인용과 AI 결과는 옅은 바탕과 안쪽 여백으로 나눠요. 기록(타임라인)은 시각 글자와 간격으로 순서를 보여요.
- [no-left-line 시험](../../apps/mobile/src/ui/noLeftLine.test.ts)이 `apps/mobile/src` 에서 왼쪽 테두리 스타일 키(`borderLeft*`, `borderStart*`)를 막아요. 좁은 View 를 세로로 세워 그린 선은 시험이 못 보니 리뷰에서 봐요.

## 화면 여백과 키보드

- 스크롤 화면의 아래 여백은 "필 높이(숨으면 안전 영역) + 24pt" 예요. 아래 입력 줄이 있으면 그 높이를 더해요. `Screen` 이 계산하고 화면은 따로 계산하지 않아요.
- 키보드가 올라오면 필은 숨고 아래 입력 줄은 키보드 위에 붙어요. 스크롤 안에 입력칸이 있는 화면만 `Screen keyboard` 를 켜서 키보드만큼 안쪽 여백을 받아요(`automaticallyAdjustKeyboardInsets`). 입력이 아래 줄이나 시트에 있는 화면에서 켜면 다른 곳의 키보드에도 스크롤이 밀린 채 남아서 끄고 둬요. 끌어서 키보드를 내릴 수 있어요.
- 입력칸 글자는 16pt, 누름 영역은 44pt 이상이에요.
